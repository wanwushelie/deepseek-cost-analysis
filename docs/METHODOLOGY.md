# DeepSeek 网页对话成本 · 计算说明

> 口径：本文所有金额均为「若用 API 跑同样内容」的等价成本。DeepSeek 网页版为免费/会员制，不按 token 计费，这些数字不是实际支付的钱。

## 一、口径声明

数据完全在浏览器本地解析，不上传任何内容。所有公式与参数列于下文，可逐项复核。

## 二、数据来源与字段语义

解析官方导出包的 `chat_sessions/*.json`，关键字段：

| 字段 | 实测语义 |
| --- | --- |
| `accumulated_token_usage` | 该轮**输入上下文大小**，不含本轮输出 |
| `fragments[].type` | RESPONSE 回答 / THINK 思考 / TOOL_* 工具 / FILE 附件 |
| `fragments[].stage_id` | 处理阶段序号，约等于该轮 API 请求次数 |
| `files[].token_usage` | 文档**全文** token（非实际读入量） |
| `PARTIAL_FILE_READ.ratio` | 网页端「只阅读了前 X%」的比例 |
| `inserted_at` | UTC 时间戳，用于峰谷与夜间优惠判断 |

**为什么确认 accum 是「上下文」而非「累计」**：

1. 多次重试均成功、单次回答字数各不相同，accum 却完全一致（若含输出应随字数变化）
2. 部分轮次（抽样中约 9%）的 accum 小于本轮输出，个别相差数倍（输入不可能小于输出）
3. 搜索结果退出上下文时 accum 会显著回落，符合「搜索结果不进后续轮次」的官方规则

## 三、输入 token

一轮对话可能触发多次 API 请求——每次工具调用后，模型都要重发完整上下文。因此：

```
总输入 = Σ轮次 ( accum × nreq )
nreq = max(1, stage_id 最大值)
更精确：第 k 次请求上下文 ≈ 上轮 accum → 本轮 accum 的线性插值
```

若不乘请求次数（等于假设工具免费），会低估约 20%。本工具采用**线性插值中性值**。

## 四、输出 token

```
输出 token = Σ (回答字数 + 思考字数 + 工具调用参数字数) × 0.362
```

系数 0.362 由官方比例（中文 0.6 / 英文 0.3 token/字符）按语料构成加权得 0.3783，偏差 4.5%。另一验证：用 accum 增量反算得 752 万，与字符法差 1.4%。

- **思考算输出**：官方 `usage.output_tokens_details.thinking_tokens` 将思考计入输出
- **工具调用参数也算输出**：查询词、URL 是模型生成的内容

## 五、联网费

| 项目 | 计费单位 | 单价 |
| --- | --- | --- |
| 网页搜索 | 每个查询词 | ¥5 / 千次 |
| 网页抓取 | 真实抓取的去重页面 | ¥5 / 千次 |
| 页内查找 | 不计费 | ¥0 |

**搜索按查询词而非调用次数**：内置工具 `deepseek_web_search` 的 `queries` 是数组，一次调用可带多个词（实测平均 4.24 词/次），3 个词计 3 次。失败或无结果不计费。

**抓取极低的原因**：深度思考搜索的 `open_page` 返回内容只给 URL/标题，`data` 为空，正文靠 `find_in_page`（不计费）从缓存取。抽样中绝大多数（约 99%）的 open_page URL 来自本会话搜索结果——服务端在搜索阶段已抓过该页，缓存命中即「内容已随搜索结果返回」，不计费。只有模型自构造的 URL（如 github/arxiv 链接）才需真实抓取。

**旁证**：open_page 返回的 snippet 中位数仅一百余字符，与搜索结果的摘要长度相当，且极少出现数千字符的长文本——若真抓全文不可能这么短。

## 七、缓存命中率

这是影响最大的单一变量。96% 是含大量 Agent 长前缀的全平台口径，**不适用于 App 聊天**。本工具按时期取值：

| 时期 | 命中率 | 性质 |
| --- | ---: | --- |
| 2025-01-10 ~ 03-24 | 56% | 官方实测 56.3% 取整 |
| 2025-03-24 ~ 08-21 | 57% | 推断 |
| 2025-08-21 ~ 2026-04-24 | 58% | 推断 |
| 2026-04-24 ~ 09-10 | 78% | 推断（V4 KV 压缩 11×） |
| 2026-09-10 起 | 88% | 推断（V4.1 再压 4×，封顶） |

**唯一硬锚点**：2025-03-01 官方《V3/R1 推理系统概览》披露 2025-02-27 24 小时数据——三端 608B 输入 token，其中 342B 命中磁盘 KV 缓存，即 56.3%。

**每 token KV 链条**：

| 版本 | 每 token KV | 关键变化 |
| --- | ---: | --- |
| V1 | 389,120 B | 基线 |
| V3 | 70,272 B | MLA（生产落盘约 39 KB） |
| V3.1 | 同 V3 | FP8 只改权重精度 |
| V3.2 | 48,068 B | DSA 索引器额外 128 维 key，反而变大 |
| V4-Flash | 3,514 B | CSA 4:1 + HCA 128:1，压缩约 11× |
| V4.1-Flash | 890 B | CED+CSA2+FP4+SWA，累计 437× |

**为何停在 88%**：官方称聊天缓存 TTL 从 7 天缩到 3 天，命中率只掉 0.5–1 个百分点，说明已近饱和；且 App 前缀不稳（思考强度写入 system prompt、模式切换都会让第 0 个 token 失效）。

## 八、R1 / V3 分流

2025-01-20 至 09-05 期间 App 同时存在 V3（非思考）与 R1（思考），**R1 单价是 V3 的 2 倍**。数据可区分：**消息内含 `THINK` 片段即为思考轮次**。

拆开后会出现反直觉结果：**R1 轮次的输入 token 可能只有 V3 的一半，费用却是其两倍**——因为 R1 输出单价 16 元，且思考内容本身算输出。

## 十、误差与限制

| 项 | 影响 | 说明 |
| --- | ---: | --- |
| 缓存命中率 | ±5~10 pp | 每降 10 个百分点，输入费涨 30–50% |
| 请求次数用 stage_id 推断 | ±20% | 输入量在基准值的 0.8~1.3 倍间浮动 |
| 字符系数 0.362 | ±5% | 官方比例加权为 0.3783 |
| V4 Pro/Flash 无法区分 | +9% | 导出包无 model 字段，默认取最低价 |

**无数据可解**：每请求 usage 明细、缓存命中率、文档 OCR 页数、工具投喂的 summary 原文、网页端上下文窗口大小。

**已知矛盾**：文档的 `ratio × token_usage` 与实际读入对不上（某大文档 ratio 显示 14%，但按全文 token 折算仅为实际读入量的几分之一），故读入量以 accum 增量为准。

## 十一、未计入的收费项（重要声明）

以下项目在官方价格表中**单独收费**，但导出包**不记录用量**，因此未计入主价格。按可推断的下限估算如下：

| 项目 | 官方单价 | 计费依据 |
| --- | --- | --- |
| 文件解析 / OCR | ¥1.5 / 千页（上传时一次性） | 文档页数 |
| 图片搜索 | ¥5 / 千次 | 调用次数 |
| TTS 语音合成 | ¥3 / 万字符（现价 ¥1.5） | 朗读字符数（中文算 2） |
| ASR 语音识别 | ¥0.78 / 小时（现价 ¥0.39） | 录音时长（按秒进位） |
| 云存储 / 云同步 | 未见单独收费 | — |
| 内容安全审核 | 未见单独收费 | — |

### 文件解析的两种估算

- **下限**：附件数 × 1 页 × ¥1.5/千
- **中估**：按类型推页数（PDF 约 30 页、PPT 约 25 页、Word 约 5 页、纯文本约 1 页）× ¥1.5/千

**量级判断**：即使按中估，这部分通常也只占总额的 1~3%，远小于缓存命中率带来的不确定性（±15%）。

### 为什么不做精确计算

导出包的 `files[].file_size` 只有字节数，**没有页数**。同样大小的 PDF，可能是几十页扫描图，也可能是上百页纯文本，无法反推。TTS / ASR 的用量更是完全无记录。

### 一个容易忽略的计费细节

文件解析是「**上传时一次性计费**」，之后再引用同一文件只付 input token。所以同一会话反复讨论一个 PDF，解析费只收一次，但上下文 token 每次都收——后者才是大头。

### 未收录但官方存在的收费项

| 项目 | 单价 | 说明 |
| --- | --- | --- |
| OCR（独立 API） | ¥1.5 / 千页 | 与文件解析同价 |
| TTS | ¥3 / 万字符 | 中文字符算 2 个，Markdown 默认剥离 |
| ASR | ¥0.78 / 小时 | 按秒计、不足一秒进位，单请求上限 120 秒 |

**结论**：本工具计算的金额仅含「模型 token + 搜索 + 抓取」三项，**不含语音与文档解析**。若你用过语音输入、语音朗读，或上传过大量 PDF / PPT，真实成本会更高——具体增量可按上表公式结合自己的用量估算。

## 十二、隐私与安全

本工具被设计成**物理上无法泄露数据**：

| 保证 | 实现方式 |
| --- | --- |
| 零网络请求 | 代码中没有任何 `fetch` / `XMLHttpRequest` / `WebSocket` / `sendBeacon` |
| 零持久化 | 不使用 `localStorage` / `cookie` / `IndexedDB`，关闭页面即清空 |
| 零外部依赖 | 无 CDN、无字体、无图片、无分析脚本，全部内联 |
| 零 XSS 面 | 文件名从不进入 DOM；动态内容都是数字或硬编码文案 |
| CSP 强制拦截 | `connect-src 'none'`——即使有恶意代码也发不出请求 |

**数据流向**：你选择的 ZIP → 浏览器内存 → 解压 → 计算 → 显示。全程不出本机。

### 部署到 GitHub Pages 有风险吗

**页面本身不会泄露**。GitHub Pages 是静态托管，不执行服务端代码，只能看到「有人访问了这个 HTML」，看不到你上传到浏览器的文件。

但要注意三件事：

1. **仓库里不要放导出包**——这是最常见的失误。JSON/ZIP 一旦提交到公开仓库，就是永久公开的
2. **不要加统计脚本**——GA、百度统计等会记录行为，且引入第三方代码
3. **用 HTTPS**——GitHub Pages 默认开启，防中间人篡改

### 如何自己验证

1. 按 F12 打开开发者工具，切到 **Network** 面板，勾选 "Preserve log"
2. 上传一个 ZIP，走完整个计算流程
3. 观察请求列表：**应该一条都没有**（或只有本地的 `file://` 读取）
4. 再切到 **Application** 面板，确认 Local Storage / Cookies 为空
5. 或者更彻底：**断网后再用**，功能完全正常

### 如何完全离线使用

1. 点击页面上方的「**保存离线版**」（或结果区底部的同名按钮）
2. 得到一个 `deepseek-账单计算器.html` 文件
3. 双击用浏览器打开，**从此不依赖任何网站**

下载的是**干净的初始版本**——不含你已经渲染的结果、不含任何个人数据。可以随便转发给别人。

### 仍然存在的风险（诚实说明）

| 风险 | 说明 |
| --- | --- |
| 浏览器扩展 | 拥有页面读取权限的扩展能看到内容。这与本页面无关，任何网页都一样。建议用无痕窗口 |
| GitHub 访问日志 | 会记录 IP、UA、访问时间，但不含你上传的文件内容 |
| 内存转储 / 崩溃报告 | 极端情况（浏览器崩溃并上传 dump），概率极低 |
| 托管平台被篡改 | GitHub Pages 用自家 CDN，风险低。**最稳妥：点页面「保存离线版」，双击离线使用**——此时连托管平台都不涉及 |

## 十三、可复核性

本工具所有计算均在浏览器本地完成，源码公开可审。核心函数：

```
readZip() / extract()   → ZIP 解析（原生 DecompressionStream）
priceOf() / proPrice()  → 各时期价格
cacheHit()              → 缓存命中率
compute()               → token 与费用计算
buildShare()            → 分享图绘制
```
