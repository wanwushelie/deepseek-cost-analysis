## 二、四条计算公式

```
① 输入 token = Σ ( accum × nreq )
   nreq = max(1, stage_id 最大值)

② 输出 token = Σ ( 回答字数 + 思考字数 + 工具调用参数字数 ) × 0.362

③ 搜索费 = 查询词数 / 1000 × ¥5        （失败或无结果的词不计费）

④ 抓取费 = 真实抓取的去重页面数 / 1000 × ¥5   （URL 已在搜索结果里的不计费）

单轮费用 = 输入/1e6 × ( 命中×命中价 + (1-命中)×未命中价 ) + 输出/1e6 × 输出价
```

## 五、快速判断规则

遇到不确定时，按这个顺序问：

1. **字段语义确认了吗？** → 用「构造反例」验证，别靠猜
2. **这个口径适用场景对吗？** → 尤其小心「全平台 vs 单场景」
3. **能被数据验证吗？** → 不能就标注为推断 + 给误差区间
4. **有没有独立路径交叉验证？** → 两条路算同一结果，差 <5% 才可信
5. **计费单位是哪个？** → 「按次」还是「按用量」还是「按去重」

## 六、错误速查（这些坑踩过了）

| 症状 | 多半是 |
|---|---|
| 费用低了 30%+ | 缓存命中率用了 Agent 口径 |
| 费用低了 20% | 按「轮」算输入，漏了工具调用引发的多次请求 |
| 输出费用明显偏低 | 漏算工具调用参数（queries/urls 也是输出） |
| 联网费高了 3 倍 | 把 `open_page` 当成 Fetch API（它返回 `data` 为空，是缓存命中） |
| 联网费低了 4 倍 | 按调用次数算搜索（应按查询词，1 次调用平均 4.24 个词） |
| 输入费与输出费不匹配 | `accum` 含了输出（它不含） |
