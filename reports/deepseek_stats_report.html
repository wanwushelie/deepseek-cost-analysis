统计口径说明
  • 累计 Token（1798 万）的真实含义 —— 此前表述有误，已修正：accumulated_token_usage 的增量拆解后证实：USER 消息增量（1,067 万）= 文档上传时的读入量，ASSISTANT 消息增量（752 万）= 输出 token（含思维链），两者合计 1,819 万。它与「之前上下文长度」的相关系数仅 0.045（上下文从 2 字涨到 5.7 万字，增量始终在 400~1,500 之间），说明该字段不包含每轮重复的上下文输入。因此不能说它是"上下文累计量"。
  • 上下文里到底有什么（官方《联网工具·多轮对话》原文）：
    · 会保留到后续轮次：用户输入、回答正文、文档内容（「历史消息引用的 file_id 文档内容会完整保留在上下文中」）；
    · 不进后续轮次：搜索结果、打开的网页、之前轮次的思考 —— 官方原文「搜索结果、打开的网页以及之前轮次的思考不会进入后续轮次的上下文，只保留回答正文」；
    · 思维链在本轮内计入上下文（带 tools 时），但不带入下一轮；
    · 文档不会静默截断，上下文超长直接返回 400。
  • 输入 / 输出 Token 拆分：两者单价不同，必须分开。
    输入 token = 9,250.5 万（Σ ASSISTANT 的 accum，字段直读）；
    输出 token = 762.7 万（字符法：回答 510.4 万 + 思维链 252.3 万；官方 output_tokens_details.thinking_tokens 印证思考属于输出）。所有版本都计入——3 次重试成功则算 3 份。
    换算系数 0.362 token/字符（≈2.76 字符/token），由「输出字符 × k」拟合，与字段实测偏差仅 1.4%。
  • 最终确定：accumulated_token_usage = 该轮次的「输入上下文」，不含本轮输出。三条证据：
    · 某会话 msg6 有 3 组搜索、accum=21,810；msg7 追问；msg8 无搜索、accum 骤降到 4,933——上一轮搜索结果退出了上下文（符合官方规则）；
    · 某会话 3 次重试全部成功（117/118/120 字），accum 却都是 91 —— 输出字数不同而 accum 不变，说明它不含输出；
    · 484 轮（9.2%）的 accum 小于本轮输出（最极端：accum=50,944 vs 输出 87,822 token）——输入不可能小于输出，反证不含输出。
    因此：总输入 token = Σ(ASSISTANT accum) = 9,250.5 万，直接用字段求和，无需任何假设。
    对应地，单轮 delta（本轮 accum − 上轮 accum）≈ 上一轮输出 + 本轮用户输入，所以之前用 delta 求和验证输出（偏差 1.4%）也是自洽的。
  • 「回退」与「分支」的真相（已核实）：两种现象必须分开看。
    ① accum 回落（如 21,810→4,933）不是分支，而是搜索结果/思考退出上下文导致上下文缩水，符合官方「搜索结果不进后续轮次」的规则。
    ② parent_id 不线性仅发生于 73 个会话（5.2%），其余 1,342 个严格线性。这 73 个是重试 / 重新生成留下的痕迹：同一句提问下并存多条 ASSISTANT，网页端 UI 显示为 < 3 / 6 > 这样的版本切换器（用户截图已确认）。
    分支点构成：165 个分支点中 TIMEOUT 87、FINISHED 66、INCOMPLETE 8、CONTENT_FILTER 3、WIP 1；112 个是空消息（68%）。单个提问最多并存 11 条尝试（2025-02/03 服务过载期）。
  • 失败重试不产生 Token 消耗（实测验证）：以某会话为例，文档 1,265 + 输入 310 字 ≈ accum 1,464；其后 8 次 TIMEOUT 的 accum 全部停在 1,464，只有成功那次升到 2,321（+857 = 输出）。另一个 11 次全失败的会话，accum 自始至终 1,464。
    → 「服务器繁忙，请稍后再试」时请求未进入推理阶段，不扣 token。因此重试不会烧钱，真正计费的只有成功的那一次。
  • 重试统计（自动识别）：全库共 54 组「同一提问多版本」、189 次尝试、53 次成功：
    · 全部成功 9 组 / 23 次 —— 主动重新生成（对答案不满意），每次都产生输出；
    · 混合 25 组 / 80 次（30 成功） —— 部分失败后重试成功；
    · 全部失败 20 组 / 86 次 —— 服务器繁忙，0 成功、不扣 token。集中在 2025-02/03 过载期。
  • 说人话：重试成功几次，就算几次输出（此前一度误判为"漏记"，已纠正）
    某会话你点了 3 次重新生成，3 次都成功（117/118/120 字），`accum` 却都是 91。起初我以为是"只记了一份"，进一步查才发现：`accum` 只记录输入上下文，本来就不含回答；而输出 token 是按字数单独算的，3 个版本各算一份，全都计入。
    结论：没有漏记，重试花了几次就记了几次。
  • 六次修正轨迹（完整留痕）：4,263 万（漏文档）→ 8,751 万（补文档重送）→ 16,190 万（误加思考/工具重送，高估 83%）→ 8,849 万（按官方规则剔除）→ 8,488 万（改为字段求和）→ 9,251 万（确认 accum 为纯输入，Σaccum 即为总输入，最终版）。
  • 为什么无法从 token 字段反推投喂量（已实测验证）：按「该轮工具结果字符量」分组比较 delta / 输出字符 比例，结果：无工具组 0.303、工具 <1k 字 0.471、1k-5k 字 0.372、5k-20k 字 0.400、>20k 字 0.414 —— 各组差异很小，且绝对值都在 0.3~0.4。极端样本更直接：某轮工具结果 48,352 字、输出 1,381 字，delta 仅 556（若工具计入应约 17,400）。证明 accumulated_token_usage 完全不含工具结果，因此无法由字段反推网页端投喂量。
  • 投喂量的合理区间（依据官方字段定义）：官方 API 文档注明 snippet 为 100-200 字符、「for display in UI」；summary 为 600-800 字符、「intended to be read by a model」。即模型读的是 summary，不是 snippet。但导出包只保存 snippet、不存 summary，故：
    · 若模型只读 top-5 的 summary：约 1,536 万字符（偏低）
    · 若读全部 26 条的 snippet：3,130 万字符（本报告采用，居中）
    · 若读全部 summary：约 8,200 万字符（偏高）
    真实投喂量落在 1,536 万 ~ 8,200 万字符之间，对应 556 万 ~ 2,968 万 token（仅本轮，不重送）。仅用于量级判断，不可当账单。
  • 工具计费规则（官方原文确认）：
    · 网页搜索：一次调用返回结果时，按查询词条数计费（3 个词 = 3 次）；失败或无结果不计费 → 本报告共发出 18,588 词，扣 22 个无结果后计费 18,566 词；
    · 网页抓取（深度思考搜索）：仅实际从网络抓取时计费，再次打开同一网页、翻页、打开已随搜索结果返回的网页均不计费 → 按去重 9,438 个页面；
    · 阅读链接：按成功抓取网页数计费，含被安全策略替换为错误的；
    · 页内查找（TOOL_FIND）不计费；图片搜索每张计 1 次；
    · usage.server_tool_use 里的 tool_search/tool_fetch/tool_image_search 才是计费次数，web_search_requests/web_fetch_requests 仅供展示、不是计费次数。
  • 文档解析费（另一笔费用，本报告无法计算）：官方《文件解析》规定 —— 上传解析成功时按页数一次性计费（OCR 价）；纯文本/表格/电子书（txt、md、csv、json、xlsx、epub 等）走 user_data，不计费。按扩展名拆分：需解析计费的是 pdf 68 + docx 44 + pptx 15 + doc 10 = 137 个；其余 642 个（md/json/txt/cs/html/xlsx 等）不计费。但导出包只记录 file_size、不记录页数，故解析费无法估算。
  • 峰谷时段（本次新算出）：按官方规则（周一至周五 09:00-12:00、14:00-18:00 为高峰，其余半价），逐条比对 10,745 条消息的时间戳：高峰仅 23.0%（2,468 条）、空闲 77.0%（8,277 条），加权系数 0.615。原因是凌晨 0-4 点活跃（2,572 条，占 24%）+ 周末占比高。这使实际单价约为高峰价的 61%。
  • 文档 token 是「解析后文本量」而非文件大小：实测 token/byte 比例 —— md 0.279、json 0.266、txt 0.207、cs 0.268、html 0.304（符合纯文本）；pdf 仅 0.0032、pptx 0.0004（文件含大量二进制/图片，但文本很少）；xlsx 高达 3.2（压缩格式，单元格文本远大于文件字节）。说明 token_usage 来自解析结果，按文本量计，与文件体积无关。
  • 字数：直接统计各 fragment 的 content 字符长度。请求 232 万 + 回答 1410 万 + 思维链 697 万 ≈ 2339 万字符。其中 35 条超长请求（>1万字，共 136.8 万字）是用户直接粘贴的文档正文，属"用户输入"与"文档内容"的双重身份。
  • 联网工具（三层数量关系，务必区分）：
    ① 搜索调用 TOOL_SEARCH 4,389 次（有效 4,310，空结果仅 79 次），共发出 18,588 个查询词（22 个无结果不计费）；
    ② 搜索返回网页 117,122 条（平均每次 26.69 条，去重 91,953 个链接）—— 这是「结果条数」，不按条计费，每个结果自带 snippet(100-200字) + summary(600-800字)，模型通常直接读摘要即可作答；
    ③ 网页抓取 TOOL_OPEN 尝试 14,349 次，其中 3,509 次为空记录（url/title/snippet 全为 null），有效 10,840 次（占搜索返回的 9.3%），去重 9,438 个页面，其中 9,324 个来自搜索结果。
    搜索与抓取是两个独立工具、各自按次计费（5元/1000次成功），官方规则「仅产生结果的请求计费」正好对应上表的 4,310 与 10,840。不可把「搜索返回的 117,122 条」当成 117,122 次调用。另 TOOL_FIND 68 次、TOOL_IMAGE_SEARCH 1 次。
  • 文档全文（1521 万）：来自 FILE.files[].token_usage，779 条记录按 file_id 去重后 737 个文件、求和 1521 万 token（未去重 1537 万，42 条重复上传）；file_size 求和 1.28 GB。这是文档全文大小，非读入量。文档正文（export_path 为 null）未随导出包保存。
  • 文档实际读入（1029 万，KPI 采用）：按每个含文档消息之后首个 ASSISTANT 的 accumulated 增量核算，单会话取 min(全文, 该轮 delta)。16 个会话触发截断，总量由 1521 万降至 1029 万（缩水 32.4%）。
  • ratio 的真实含义（已由网页端 UI 截图确认）：网页端会显示「超出字数限制，DeepSeek 只阅读了前 X%」，X 与 PARTIAL_FILE_READ.ratio 逐一吻合（14.04→14%、26.55→26%、47.12→47%、87.52→87%）。所以 ratio = 读取了文件的「前 X%」（按字符计的前缀）。
    关键现象：四个文档 ratio 从 14% 到 87% 差异巨大，但实际读入 token 全部收敛在 89~91 万 —— 说明网页端存在一个固定的字符读取上限（约 90~100 万字符，接近 1 token/中文字符），ratio 只是「该上限 ÷ 全文总长」的结果。
    但不能用 ratio × token_usage 去算：网游小说 172.5万×14.04%=24.2万，与实际 89.3 万不符 —— 因为 token_usage 的换算比例与网页端实际 tokenizer 不一致。读入量仍以 delta 为准。
    佐证：考研真题会话里模型自述「最后一条 2023 被截断了（content end 但 JSON 不完整）」，印证了前缀截断的物理行为。
  • 图片 token —— 字段直读，无需计算：来自 files[].token_usage，239 张全部有原生值且无重复，求和 10.18 万 token（平均 426/张）。与官方规则交叉验证通过：官方「每张图上限 1024 token」，实测 238 张 ≤1024（最大 1010），仅 1 张异常 2530（无宽高数据，疑为拼接图）。此项为字段直读，非估算。
  • 哪些是字段直读、哪些是推算（重要）：
    · 字段直读：图片 token（files[].token_usage）、文档全文字数（同上）、输出 token（accumulated 增量，已验证偏差 1.4%）、会话累计 token；
    · 必须推算：输入 token —— 导出包没有 per-request 的 usage.prompt_tokens / completion_tokens 字段，只有一个会话级累计值，无法直接得到每轮重送的上下文量，故只能用字符 × 系数推导。
  • 换算系数 k=0.362 的官方校验：官方文档给出「1 中文字符 ≈0.6 token、1 英文字符 ≈0.3 token」。实测本文本构成：中文 36.3%、英文 28.1%、数字 2.9%、标点 16.8%、空白 15.9%。按官方比例加权得 k=0.3783，与实测 0.362 相差仅 4.5%，系数可靠。
  • 附件会话数（修正）：有 FILE 片段的会话是 312 个（193 含文档 + 131 含图片，有重叠）；其中仅 131 个会话的图片被实际导出到 *_files/ 目录。此前写的"131 个会话含附件"是把"含图片会话"误当成了"含附件会话"。
  • 数据质量提示：status 字段不完全可靠 —— 3,509 个空抓取记录仍标为 FINISHED；另有 6 条 ASSISTANT 消息状态 FINISHED 却无 RESPONSE 内容。消息级异常共 189 条无回答（TIMEOUT 140 / INCOMPLETE 32 / CONTENT_FILTER 11 / 其余 6）。
  • 重新生成的真实 Token 影响（很小）：213 次 accum 回落幅度合计 27.96 万，但这只是上下文缩水的幅度（搜索退出导致），不是花费。真正因"多版本并存"而重复计入的量 = sum(delta) − sum(max) ≈ 21.4 万，仅占总 token 的 1.2%。加上失败重试不扣 token，重试与重新生成对该账号的总消耗影响可忽略。
