01数据源与字段语义

数据来自 DeepSeek 网页版「导出全部对话」生成的 ZIP，解压后为 chat_sessions/*.json，每个文件一个会话。关键字段只有六个，但每个的语义都需要实测确认——这是整个计算中最容易出错的地方。

字段路径实测语义
accumulated_token_usagemessage 级该轮次的输入上下文大小，不含本轮输出
fragments[].typeRESPONSE / THINK / REQUEST / TOOL_* / FILE区分回答、思维链、用户输入、工具调用、附件
fragments[].stage_idfragment 级处理阶段序号，一个阶段约等于一次 API 请求
files[].token_usage附件级文档全文 token（非实际读入量）
PARTIAL_FILE_READ.ratio文档级网页端读取了文件前 X% 的比例
inserted_atmessage 级UTC 时间戳，用于峰谷/夜间优惠判断

为什么必须先确认 accumulated 的语义

若它表示「会话累计消耗」，直接求和即可；若表示「当前上下文」，则需要乘以请求次数。三条实测证据指向后者：

  1. 输出字数不同但 accum 相同：某会话 3 次重试全部成功（回答 117 / 118 / 120 字），三条 accum 却都是 91。若含输出，值应随字数变化。
  2. 存在 accum 小于本轮输出：全库 484 轮（9.2%）出现这一现象，最极端一例 accum=50,944 而输出 87,822 token。输入不可能小于输出。
  3. 会因搜索退出而下降：某轮带 3 组搜索时 accum=21,810，下一轮无搜索骤降至 4,933。符合「搜索结果不进后续上下文」的官方规则。
结论：accumulated_token_usage 是「该轮结束时的上下文快照」，是输入而非累计消耗，且不含本轮输出。

02输入 token：最容易算错的一环

朴素做法与它的漏洞

直觉上，总输入 = 所有轮次 accum 之和。对这份数据，得到 9,251 万。

但这忽略了一个结构性事实：一轮对话往往对应多次 API 请求。当模型调用工具（搜索、抓取）后，工具结果要回传，模型必须重发完整上下文才能继续生成。所以一带工具的轮次，实际是 2~3 次请求，每次都要付输入费。

总输入 = Σ轮次 ( accum × nreq )
其中 nreq = max(1, stage_id 最大值)，表示该轮实际请求次数

请求次数怎么定

导出包没有直接的请求计数，只能用 stage_id 推断。全库统计：

每轮请求数轮次数占比
1 次（纯对话，无工具）2,89253.2%
2 次1,63130.0%
3 次82815.2%
4 次以上891.6%
合计9,046 次请求 / 5,440 轮1.66 次/轮

因为工具可以并行批量调用（官方文档：「模型一次调用多个工具时，先下发全部调用块，再下发结果块」），所以 6 个工具的轮次 stage 最大仍可能只有 2 —— 不能用「工具数 + 1」估算，会高估到 4.46 次/轮。

三种口径的取值

口径总输入相对说明
每轮 1 次9,251 万1.00×低估，等于假设工具调用免费
线性插值（采用）11,252 万1.22×第 k 次请求上下文 ≈ 上轮 accum → 本轮 accum 的线性插值
accum × 请求数11,763 万1.30×上界，假设每次请求都用最大上下文
这一层的误差：stage_id 是否真等于请求次数，无法从数据反证。若实际请求数更多（如每次工具单独一次往返），输入会进一步上升；若更少（如服务端合并多轮工具），则接近 9,251 万。当前取中性值 11,252 万。

03输出 token：按字符折算

导出包没有 per-message 的 output_tokens，只能用字符数折算：

输出 token = Σ ( len(RESPONSE) + len(THINK) ) × k
k = 0.362 token/字符（≈ 2.76 字符/token）

为什么思维链算输出

官方 usage.output_tokens_details.thinking_tokens 明确把思考 token 归入输出。这份数据里思维链占输出字符的 33%（697 万 / 2,107 万），不能忽略。

k 值的校验

官方换算比例为「1 中文字符 ≈ 0.6 token，1 英文字符 ≈ 0.3 token」。实测本文本构成：

字符类型占比官方系数
中文36.3%0.6
英文28.1%0.3
数字2.9%0.3
标点符号16.8%~0.4
空白15.9%并入相邻

按官方系数加权得 k = 0.3783，与实测 0.362 相差 4.5%。另一条独立验证：用 accum 增量反算输出（delta ≈ 上轮输出 + 本轮用户输入），得到 752 万，与字符法 762.7 万相差 1.4%。

结论：k = 0.362 可靠，误差约 ±5%。总输出 762.7 万 token。

04联网费：按查询词与页面计

联网按查询词条数计费，而非「调用次数」——这是最容易被算错的一处。一次搜索调用可以批量发多个查询词，每个词各计一次。

项目原始量计费单位计费量费用
网页搜索4,389 次调用查询词条数18,566 词¥92.83
网页抓取10,840 次调用真实抓取页面118 个¥0.59
页内查找68 次不计费0¥0
合计—¥5 / 1,000 次18,706¥93.42

官方规则（《联网工具·用量与计费》）

  • 搜索：一次调用返回结果时，按 input.queries 内的查询词条数计费（3 个词 = 3 次）；失败或无结果不计费。
  • 抓取（深度思考搜索）：仅实际从网络抓取时计费。再次打开同一网页、翻页、打开已随搜索结果返回的网页均不计费。
  • 页内查找：不计费。
  • usage.server_tool_use 里的 tool_search/tool_fetch 才是计费次数；web_search_requests 仅供展示。
计费口径：搜索按查询词（内置工具口径）；抓取按真实抓取页面——98.8% 的 open_page URL 来自本会话搜索结果（服务端缓存命中，不计费），仅 118 个模型自构造 URL 计费。为什么抓取这么便宜：搜索 ¥5/千次是「检索 + 抓取 N 个页面 + 生成摘要」的打包价（本数据平均每次返回 26.69 条），页面内容在搜索阶段已抓过；open_page 只是「深入看某个已抓过的页面」，再收一次就是重复计费。

这是影响最大的单一变量。常见错误是直接用「全平台 96%」——那是含大量 Agent 长前缀的口径，App 聊天不适用。

唯一硬锚点：2025-03-01 官方《V3/R1 推理系统概览》披露 2025-02-27 12:00 至 02-28 12:00 的 24 小时统计——三端共 608B 输入 token，其中 342B 命中磁盘 KV 缓存，即 56.3%。当时 App 刚上架、Agent 流量未成形，可近似聊天基线。

为何 2025 全年不跃升：KV 没变小（V3.2 反而增大），缓存 TTL 仍为「尽力而为、几小时到几天」，只能贴着 56% 微升。

为何停在 88% 而非 96%：官方称聊天缓存 TTL 从 7 天缩到 3 天，整体命中率只掉 0.5–1 个百分点——说明回访长尾基本落在 3 天内，继续扩容已近饱和。且 App 侧前缀本身不稳（思考强度写入 system prompt、模式切换、会话重置都会让第 0 个 token 起失效）。

6.2 三个反直觉结论

① 输出只占 7.6% 的 token，却占 17% 的费用

输入 11,252 万 token 对输出 763 万，比例 15:1；但费用比是 30:35.6。因为输入单价被缓存打到 0.02–0.5，输出是 2–16，差 6–60 倍。

② 联网比模型本身贵 2.2 倍

联网 ¥93.42 vs 模型 ¥67.53。搜索一项占总价 58%。原因是按查询词计费——4,389 次调用平均每次发 4.24 个词；抓取几乎免费（缓存命中）。

③ 全程用新模型反而更便宜

若全部 5,440 轮都按 V4.1-Flash 现价（0.02–0.04 / 1–2 / 4–8）+ 88% 缓存，总价 ¥153.42，比按当时真实价格的 ¥160.95 还低 5%。因为 2025 年 V3 的输入价 0.5 是今天的 25 倍。

6.4 自审发现的修正项（审计于 2026-11-18）

漏算：工具调用指令未计入输出——模型生成查询词、选择 URL 的参数也是输出。实测 122 万字符 ≈ 44.2 万 token，占已算输出的 5.8%，约 ¥2。修正后输出为 807 万 token（原 763 万），总价约 +1%。
已解决：open_page 的计费口径（2026-11-18 二次核查）——官方文档说明「深度思考搜索里打开的网页，只给 URL、标题和发布时间，data 为空字符串，页内正文要靠页内查找（find_in_page）去取」，而 find_in_page 完全不计费。工程逻辑链：搜索时服务端已抓取网页生成 summary（缓存已存在）→ open_page 从搜索结果选 URL = 缓存命中，不从网络抓取，不计费。实测 10,840 次 open_page 中 98.8% 的 URL 来自本会话搜索结果（不计费），仅 131 次是模型自构造 URL（github/arxiv 等，真实抓取，计费 ¥0.59）。
修正前后对比：抓取费 ¥47.19 → ¥0.59；联网费 ¥140.13 → ¥93.42；总价 ¥205.74 → ¥160.95（-23%）。
强力旁证（内容长度）：open_page 返回的 snippet 中位仅 125 字符（搜索结果 192 字符），分布 64% 在 1–299 字、0 条超过 5,000 字。若真抓全文，不可能只有 125 字。另有 3,509 次 open_page 无 url（失败调用），不计费。
最坏情况：若假设 10,709 次缓存命中全部改为真实抓取，抓取费升至 ¥53.5，总价约 ¥214——但这与「snippet 仅 125 字」的事实矛盾。
澄清：不存在"更便宜的计费口径"（2026-11-18 三次核查）——内置工具 deepseek_web_search 的 input.queries 是数组，一次调用可带多个查询词（本数据集平均 4.24 词/次），按词计费。独立 Search API 的 query 是单个字符串（1–128 字符），复刻同样效果需发 18,566 次请求，费用完全相同（¥92.83）。
此前误算的「按调用次数 ¥21.55」是把 4,310 次调用当成 4,310 次计费，等于假设每次只查 1 个词——与实际 4.24 词/次不符，该口径不存在，已删除。
已验证无误的项：¥5/千次单价（官方双语 ¥5 = $0.75）；失败搜索不计费（实测仅 22 个查询词）；TIMEOUT 不扣 token（accum 不变）；k=0.362（双重验证）；按 THINK 分流 R1/V3。近似项：线性插值在 5+ 工具的轮次偏差可达 30%+（上下文非线性增长）；同轮内第 2+ 次请求的缓存命中率应高于时期均值（当前保守统一取值）。

7.2 网页端内部行为（官方未公开）

  • 文档截断规则：UI 提示「超出字数限制，只阅读了前 X%」，X 与 PARTIAL_FILE_READ.ratio 一一吻合（14/26/47/87%）。但四个大文档的 ratio 差异巨大，实际读入 token 却都收敛在 89~91 万——说明存在固定字符读取上限（约 90~100 万字符）。但 ratio × token_usage 与实际读入对不上（网游小说 172.5 万 × 14% = 24.2 万，实际 89.3 万），这个矛盾未解，读入量仍以 accum 增量为准。
  • 工具投喂 top-N：官方注明 snippet 是「for display in UI」、summary 是「intended to be read by a model」。模型实际读到几条 summary 未知，工具结果 token 误差可能达 ±1 倍。
  • 网页端是否完全遵循 API 多轮规则：本报告假设一致（搜索结果/思考不进后续轮次），未证实。
  • 网页端上下文窗口：峰值实测 96.1 万，推测 100 万，未确认。
