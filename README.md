## 一、项目是怎么演进的

这个项目实际经历了**三个阶段**，每个阶段的产出完全不同：

```
阶段 1  数据洞察      →  deepseek_stats_report.html   （你的对话长什么样）
阶段 2  成本方法论    →  deepseek_cost_methodology.html（钱是怎么算出来的）
阶段 3  交付工具      →  deepseek_cost_calculator.html （给别人自己算）
```

一开始只是想「看看我的 DeepSeek 都聊了什么」，后来发现真正有意思的问题是**「这些对话在 API 上值多少钱」**，然后这个数字又被反复质疑、反复修正了 8 次。

**回头看，阶段 3 才是最该一开始就做的。** 阶段 1、2 产生的所有认知，最终都变成了工具里的一条条计算规则和一段可复制的 Markdown。

## 二、最值钱的一次失误：¥42.48 → ¥62.85

初版结果 **¥42.48**。中间发现缓存命中率用错了。

我当时用的是官方公告里的「**全平台 96%**」。但 DeepSeek 后来提供的分析指出：

> 96% 是含大量 Agent 长前缀的口径（Agent 每轮重发 77K token 的系统提示+工具定义+代码库，真正的增量只有几百 token）。**App 是普通聊天，没有这种重复结构。**

改成 App 侧的分时期取值（56% → 88%）后，总费用跳到 **¥62.85（+48%）**。

**教训：口径的适用边界比口径本身重要。** 一个正确但用错场景的数字，比一个粗糙但场景匹配的数字错得更远——而且更难被发现，因为「96%」看起来更权威。

## 四、五个关键认知

### 1. `accumulated_token_usage` 是「上下文快照」，不是「累计消耗」

这是整个分析的地基。三条实测证据：

1. 3 次重试全部成功（回答 117 / 118 / 120 字），三条 `accum` 却都是 **91**——若含输出，值应随字数变化
2. 全库 **484 轮（9.2%）** 出现 `accum` 小于本轮输出，最极端 `accum=50,944` 而输出 `87,822` token——输入不可能小于输出
3. 搜索结果退出上下文时 `accum` 从 21,810 骤降到 4,933——符合官方「搜索结果不进后续轮次」规则

**如果搞错这一条，后面全是错的。** 而它是靠实测发现的，不是靠读文档猜的。

### 2. 一轮对话 ≠ 一次 API 请求

52% 的轮次带工具调用（共 18,807 次）。每次工具结果返回后，模型必须**重发完整上下文**。

- 5,440 轮 → **9,046 次实际请求**（1.66 次/轮）
- 按 1 次算，等于假设工具调用免费 → 低估 22%

多个工具是**并行批量调用**的（官方：「先下发全部调用块，再下发结果块」），所以请求次数要看 `stage_id` 而不是「工具数 + 1」——后者会高估到 4.46 次/轮。

### 3. 输出只占 7.6% 的 token，却占 23% 的费用

输入 11,252 万 vs 输出 807 万，比例 14:1；费用比却是 30:37.5。

原因有三层叠加：
- 输出单价本就是输入的 2~4 倍
- **96%→88% 的缓存命中率让输入打到 0.02~0.5 元/百万**
- **思考内容算输出**（R1 的 16 元/百万是最贵的）

### 4. 联网费 68% 里，搜索按「查询词」计费而不是「调用次数」

一次搜索平均发 **4.24 个改写查询**（深度思考的检索扩展），4,389 次调用共 18,588 个词。

我一度以为「按调用次数只要 ¥21.55」是更便宜的口径——**那是算错了**，独立 Search API 的 `query` 是单个字符串，复刻同样效果要发 18,566 次请求，费用相同。

### 5. `open_page` 返回的 snippet 只有 125 字符

这是「抓取费近乎为零」最硬的物理证据：

| 内容来源 | snippet 长度中位 |
|---|---|
| 搜索结果 | 192 字符 |
| **open_page 返回** | **125 字符** |

分布上 64% 在 1~299 字，**0 条超过 5,000 字**。真抓了全文不可能这么短。

加上官方的两条佐证（`data` 为空字符串、`find_in_page` 完全不计费），才能确定抓取费是 ¥0.59 而非 ¥47.19。

## 五、踩过的坑（与技术无关的那些）

### 1. 把个人数据写进通用文档

「计算说明」里写了「779 个文档附件」「PDF 68×30 页」「¥1.17~5.01」——这是我这份数据的数字，但文档是要给所有人看的。

**正确做法**：只写公式与方法（`附件数 × 1 页 × 单价`），官方事实可以写（56.3%、KV 字节数、单价表），个人数据一律不写。

### 2. `<label>` 内联布局导致的边框碎片

上传区用 `<label>` 包 `<div>`，HTML 禁止 inline 元素包含 block 元素，浏览器强制拆包，虚线边框被撕成两片散在左边。**桌面 Chrome 严格暴露，手机浏览器反而静默修正**——所以这种问题往往在手机上测不出来。

修法：`.drop{display:block}`。

### 3. 手机端选文件要选两遍

```js
drop.addEventListener("click", () => fileInput.click());   // 多余
```

`<label>` 本就关联 input，再手动触发就是「双重打开选择器」，手机上两个选择器排队弹。

另外 `display:none` 的 input 在 iOS 上可能让 label 失效，改用标准 `sr-only` 视觉隐藏。

### 4. 被截图工具误导，差点去改没坏的 CSS

截图里文字被右切，注入测量脚本后发现：`vw=496` 而截图只有 430 宽——**Edge 无头模式的最小窗口宽度是 496px，我设的 430 无效**。页面本身没问题。

**差点为一个不存在的问题改代码。**

### 5. 把 `open_page` 当成 Fetch API

想当然认为「打开网页 = 抓取网页」。直到读到官方那句「`data` 是空字符串，也没有 `signature`」才意识到——一个不返回内容的调用，凭什么要按抓取收费。

## 六、方法论沉淀

这几条是可以直接用在下一个类似项目上的：

| 原则 | 具体做法 |
|---|---|
| **字段语义必须实测** | 不靠文档猜，用「构造反例」验证。accum 用三条独立证据交叉确认 |
| **每个假设都要问：能被数据验证吗** | 不能的（缓存命中率、模型版本）就明确标注为推断并给误差区间 |
| **交叉验证** | 用两条独立路径算同一结果：字符法 0.362 vs accum 增量法，差 1.4% |
| **口径要写清适用边界** | 「96%」不是错，是「用错场景」。文档里必须写「这是 Agent 口径，App 不适用」 |
| **保留错误记录** | 修正过程写进文档（「此前误算的 ¥21.55 是…」），便于审计追溯 |
| **反向验证** | 算出 ¥0.59 的抓取费后，主动去找「它是不是该更高」的证据（snippet 长度、官方规则） |

## 九、如果重来

1. **先做工具，再做报告。** 所有踩的坑在工具里只需要修一次，报告里要修三次（报告、方法论、工具各一份）。
2. **先写口径声明再写代码。** 「96% 是不是 App 口径」这个问题如果第一天就问，能省掉 ¥20 的错误结论和一整轮返工。
3. **边算边写 Markdown。** 方法论文档如果是最后凭记忆补的，一定会漏掉中间那些「为什么不这样算」的推理——而那恰恰是最有价值的部分。
4. **给每个数字标注来源等级**：官方实测 / 官方文档 / 数据推断 / 经验估计。混在一起时，人就没法判断该信哪个。
5. **外部来源的 HTML 也要审计。** 本项目后期收到的视觉重构版，同样先过了网络请求 / 持久化 / 动态执行 / CSP 四项检查才纳入——「界面做得好」和「能不能安全地跑」是两件事。
